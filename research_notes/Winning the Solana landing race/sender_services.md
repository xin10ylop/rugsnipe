# Commercial Solana transaction-submission ("sender" / "landing") services, October 2026 — comparison for a Frankfurt bare-metal pump.fun sniper

Research date: 2026-10-18. Everything below is what the vendor docs / blogs say as of this date unless marked "measured". Vendor claims are labelled as such. Anything the user already knows (Helius key = 50 req/s, Jito bundleOnly = no tip on failure, Nozomi min tip 0.001 SOL, BlockRazor min tip 0.0001 SOL) is only restated where needed for context.

Global context that affects every service:
- Solana slots moved from 400 ms to 200 ms at epoch 1053 on 9 Oct 2026 (separate from Alpenglow); BAM's auction cadence therefore tightened from 25 ms to 20 ms automatically — [Solana Compass / Jito changelog](https://solanacompass.com/news/jito-details-bams-alpenglow-plan-maintenance-mode-for-all-mainnet-nodes-no-firebam-during-the-transition)
- Alpenglow mainnet activation is scheduled for epoch 1064, Wed 21 Oct 2026 ≈15:00 UTC (page treats it as an estimate); the gate flips at epoch start, TowerBFT runs for the first 5,000 slots (~18 min), Alpenglow consensus takes over at slot 459,653,000. Transaction formats, fees, signing, sending are unchanged. PoH ticks disappear from the shred stream, so "how far into the slot is the leader" logic based on tick counts breaks; Anza recommends a local slot clock corrected for latency to the leader — [solana.com/upgrades/alpenglow](https://solana.com/upgrades/alpenglow)
- Jito will put all mainnet BAM nodes into Maintenance Mode "in the days leading up to activation"; connected validators revert to ordinary Jito-Agave Block Engine mode; Block Engine bundles and FullSend keep working; MPP and DBI are unavailable during the window; BAM nodes return "gradually" afterwards. No fixed start/end published — [Solana Compass](https://solanacompass.com/news/jito-details-bams-alpenglow-plan-maintenance-mode-for-all-mainnet-nodes-no-firebam-during-the-transition)

## Key question 0 — Per-service profiles (one subsection per service)

### Takeaway
Nearly every commercial sender is one of three things: (a) a Jito/Harmonic bundle relay, (b) a SWQoS-staked TPU forwarder with a mandatory SOL tip, or (c) both at once (Helius Sender, Nozomi, NextBlock, Astralane, BlockRazor, bloXroute "Fastest"). The practical differences for a Frankfurt box are: minimum tip, whether the tip is an on-chain instruction (paid only if the tx lands/succeeds) or a server-side parameter, rate limit at the free tier, whether there is a Frankfurt and an Amsterdam PoP, and whether the service penalises fan-out to competitors.

### Cited Findings

#### Jito Block Engine (bundles, sendTransaction, bundleOnly)
- Regional block-engine endpoints (mainnet): global `mainnet.block-engine.jito.wtf`; **Amsterdam** `amsterdam.mainnet.block-engine.jito.wtf` (shred receiver 74.118.140.240:1002); Dublin; **Frankfurt** `frankfurt.mainnet.block-engine.jito.wtf` (shred receiver 64.130.50.14:1002, NTP `ntp.frankfurt.jito.wtf`); London; New York; Salt Lake City; Singapore; Tokyo — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- `sendTransaction` is `/api/v1/transactions`, "acts as a direct proxy to the Solana sendTransaction RPC method", "forwards your transaction directly to the validator", "By default, it submits the transaction with providing MEV protection"; `bundleOnly=true` → "the transaction is sent exclusively as a single transaction bundle" and is presented as the revert-protection / "cost efficiency" option; `skip_preflight=true` is always set; base64 encoding recommended, base58 deprecated; `x-bundle-id` response header carries the bundle id — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- Minimum tip 1,000 lamports for bundles ("may not be enough during high demand"); max 5 transactions per bundle; 8 tip accounts ("have remained constant"), pick one at random to reduce write-lock contention; tip may be any top-level or CPI SOL transfer to a tip account; do not put tip accounts in an ALT; "Tips do not prioritize transactions for validators that are not Jito-Solana leaders"; for `sendTransaction` Jito recommends a 70/30 split priority-fee/tip, for `sendBundle` "only the Jito tip matters" — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- Tip-floor API: REST `https://bundles.jito.wtf/api/v1/bundles/tip_floor`, fields `landed_tips_25th/50th/75th/95th/99th_percentile`, `ema_landed_tips_50th_percentile` (units are SOL, undocumented on the page); WebSocket `wss://bundles.jito.wtf/api/v1/bundles/tip_stream`; dashboard `explorer.jito.wtf/tip-floor` — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- Live sample pulled 2026-10-18T16:27Z: 25th 2.98e-6 SOL, 50th 7.76e-6, 75th 1.06e-5, 95th 1.5e-4, 99th 1.02e-3, EMA-50th 6.87e-6 — [tip_floor API](https://bundles.jito.wtf/api/v1/bundles/tip_floor)
- Rate limit: "1 request per second per IP per region" by default; 429 on breach; no approved auth key needed for default sends; UUID auth via header `x-jito-auth: <uuid>` or `?uuid=`; higher limits via Discord ticket — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- Auction: "Parallel auctions are run at 50ms ticks"; bundles execute sequentially and atomically within one slot; `sendBundle` returns a bundle_id immediately ("does not guarantee the bundle will be processed or land on-chain"); `getInflightBundleStatuses` (5-min lookback: Failed / Pending / Landed / Invalid), "Failed" means all regions that received the bundle marked it failed; uncled blocks can cause bundle txs to land unbundled (losing atomicity/revert protection) — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- `jitodontfront`: any pubkey starting with `jitodontfront` in any instruction; bundles containing such a tx are rejected unless that tx is at index 0 (multiple allowed only if contiguous at the front and sharing a signer); works with both `sendBundle` and `sendTransaction`; "may help reduce sandwich attacks but is not guaranteed to do so" — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- Protocol fee: Jito charges 6% on tips (post JIP-24, Aug 2025, 100% of that 6% goes to the DAO) — [tokenomics.com](https://tokenomics.com/articles/jito-tokenomics-how-jto-captures-mev-and-staking-revenue-on-solana); Harmonic docs independently state "Jito's 6% cut" — [Harmonic FAQ](https://docs.harmonic.gg/reference/faq)
- The docs page says nothing about deduplication, multi-region fan-out policy, bans, durable nonces, BAM or Alpenglow — [Jito docs](https://docs.jito.wtf/lowlatencytxnsend/)
- Stake coverage (conflicting figures): Jito's Q2-2026 token-holder report puts the Jito client family (Jito-Labs + Jito-BAM) at ~54% of active stake and BAM alone at ~33% — [Blockworks / Jito Q2 2026 report](https://blockworks.com/api/investor-report/jito-token-holder-report-q2-2026/pdf); Jito's 9 Oct 2026 changelog says BAM-connected validators hold 164M SOL = 37% of stake across 385 validators (epoch 1050) — [Solana Compass](https://solanacompass.com/news/jito-details-bams-alpenglow-plan-maintenance-mode-for-all-mainnet-nodes-no-firebam-during-the-transition); Triton's blog says "JitoBAM (60% of active stake) and Harmonic (16%)" — [Triton blog](https://blog.triton.one/swqos-for-everyone-why-we-retired-cascade-marketplace/); a Crypto Briefing piece claims Jito client on ">95% of active stake" — [Crypto Briefing](https://cryptobriefing.com/jito-351m-market-cap-78m-mev-fees-solana/); a vendor blog says Jito bundles only work in "~65% of slots" — [dev.to (AllenHark promo)](https://dev.to/techmystique_/the-fastest-way-to-land-solana-transactions-in-2026-5gg9)
- Jito ShredStream: a competitor (OrbitFlare) reports Jito's ShredStream shut down completely on 5 Sep 2026 with Jito pointing users to DoubleZero Edge — [OrbitFlare](https://orbitflare.com/blog/developers/jito-shredstreams-last-slot); the D3AD-E sniper INFRA.md repeats "Jito ShredStream shuts down on 5 September 2026" — [INFRA.md](https://raw.githubusercontent.com/D3AD-E/Solana-sniper-bot/main/INFRA.md). I did not find Jito's own notice.

#### Jito BAM (Block Assembly Marketplace) and Direct Bundle Ingest (DBI)
- BAM launched on mainnet in September 2025 (one source says July); it is Jito's TEE-based scheduler network (BAM Nodes) with a plugin system; validators run AgaveBAM or FireBAM — [Blockworks](https://blockworks.com/news/jito-bam-solana-mainnet); [bam.dev docs](https://bam.dev/docs/bam/bam-overview/)
- Submission path per validator docs: "Transactions and Bundles are ingested by the BAM Node, which validates, sequences and finally sends them to the leader BAM Validator"; RPC-submitted transactions to a BAM-connected validator "scheduled to lead soon" are routed through BAM; transactions sent to the TPU port are processed through BAM before execution; the BAM Node keeps one Block Engine connection per validator "to maintain backwards compatibility" — [bam.dev docs](https://bam.dev/docs/bam/bam-overview/)
- DBI (announced 13 Oct 2026, live for an early cohort for ~1 month before): bundles submitted directly to a BAM node over QUIC or JSON-RPC, bypassing the Block Engine's "roughly 50ms per hop"; **whitelist-only** via application form, no published approval criteria; Block Engine bundle and `sendTransaction` traffic is now forwarded to BAM through DBI; stated goal is that Block-Engine-centric searchers "fully move to DBI on BAM leader slots" — [Solana Compass](https://solanacompass.com/news/jito-announces-bam-direct-bundle-ingest-routing-solana-bundles-past-the-block-engines-50ms-hop)
- Jito's own before/after (3–20 Sep vs 20 Sep–7 Oct 2026): bundles received −7.5% (23.76B→21.97B), bundles landed +16.9% (106.3M→124.3M), end-to-end land rate 0.45%→0.57%, simulation success 11.4%→16.1%, compute wasted on failed sims 50%→41%, landed-bundle tips 14,279→28,765 SOL, reward per landed bundle +72%. Jito does not separate DBI-direct from forwarded bundles — [Solana Compass](https://solanacompass.com/news/jito-announces-bam-direct-bundle-ingest-routing-solana-bundles-past-the-block-engines-50ms-hop)
- Ordering under DBI/BAM: signatures checked, bundle simulated, any failing bundle dropped; survivors ranked "by total fees (priority fees plus Jito tips) relative to requested compute"; winners executed as a batch; whole bundle reverts if any tx fails — [Solana Compass](https://solanacompass.com/news/jito-announces-bam-direct-bundle-ingest-routing-solana-bundles-past-the-block-engines-50ms-hop)
- Fees: no separate BAM submission fee is documented; tips remain Jito tips (6%); plugin fees accrue to validators (amounts not given) — [bam.dev](https://bam.dev); [tokenomics.com](https://tokenomics.com/articles/jito-tokenomics-how-jto-captures-mev-and-staking-revenue-on-solana)
- BAM does not "replace" the Block Engine today: the Block Engine remains the authentication/simulation/filter front-end for non-whitelisted flow and the fallback during Alpenglow maintenance — [Solana Compass DBI](https://solanacompass.com/news/jito-announces-bam-direct-bundle-ingest-routing-solana-bundles-past-the-block-engines-50ms-hop); [Solana Compass Alpenglow plan](https://solanacompass.com/news/jito-details-bams-alpenglow-plan-maintenance-mode-for-all-mainnet-nodes-no-firebam-during-the-transition)
- Regional BAM node locations are not published in any source I found.

#### Helius Sender
- Routing: each request is fanned out to "Helius, Jito, Harmonic, and Rakurai, etc." simultaneously (Sender Max); SWQoS-only tier (`?swqos_only=true`) uses a single Helius SWQoS path — [Helius Sender docs](https://www.helius.dev/docs/sending-transactions/sender.md)
- Regional HTTP endpoints: `slc-`, `ewr-`, `lon-`, **`fra-sender.helius-rpc.com`**, **`ams-sender.helius-rpc.com`**, `sg-`, `tyo-`; global HTTPS `sender.helius-rpc.com/fast` for browsers; `/ping` per host; warm the connection if idle >5 s — [Helius Sender docs](https://www.helius.dev/docs/sending-transactions/sender.md)
- Tip tiers: Sender Max min 0.001 SOL (enters "priority tip buffer" that "favors the highest tips"); SWQoS-only min 0.000005 SOL; tips between the two are best-effort through fewer pathways; every tx must carry both a tip transfer and a compute-unit-price instruction or it is rejected; min priority fee 5,000 lamports, ≥10,000 recommended; 10 tip accounts (listed in docs) — [Sender Max docs](https://www.helius.dev/docs/sending-transactions/sender-max.md); [Sender docs](https://www.helius.dev/docs/sending-transactions/sender.md)
- Rate limits: keyless 1 req/s per egress IP per region (NAT-shared, 429s count, `/ping` doesn't); with key 50 req/s per key per region; ">50 req/s require an approved dedicated Sender key" (pricing not published; "contact sales") — [Sender docs](https://www.helius.dev/docs/sending-transactions/sender.md)
- Bundles: `sendBundle` up to 4 fully-signed txs, atomic; only one tx needs the 0.001 SOL tip; "Helius adds pathway tips, including Jito's, on your behalf. Don't add a Jito tip, use Jito tip accounts, or set the jito-region header"; tracked by any member signature, no bundle ids — [Sender Max docs](https://www.helius.dev/docs/sending-transactions/sender-max.md)
- `mev-protect=true` routes around validators statistically linked to sandwiching; works on both tiers and both methods — [Sender Max docs](https://www.helius.dev/docs/sending-transactions/sender-max.md)
- Claimed latency: "typical land-time is ≤ 1.5 slots" with seven regional endpoints (vendor claim, no methodology) — [Helius Sender FAQ](https://www.helius.dev/docs/faqs/sender.md)
- Helius guide: `skipPreflight: true`, `maxRetries: 0`, rebuild with a fresh blockhash + re-priced fee rather than resending; durable nonces not mentioned; dedup/multi-region fan-out not covered — [Land trades guide](https://www.helius.dev/docs/sending-transactions/guides/land-trades-with-sender.md)
- Pathway "Rakurai" is a jito-solana fork with a proprietary closed-source scheduler loaded at runtime; Figment migrated its primary validator to it on 2 Mar 2026 and reports yield 6.85%→7.17% — [Figment](https://www.figment.io/insights/figment-upgrades-solana-infrastructure-with-rakurai-client/)
- Helius's own public benchmark page ranks *RPC providers'* send paths, not third-party senders: last-24h "Balanced" workload across 6 regions — Helius 84.9% landed, slot p50/p95 = 5/7; Chainstack 77.1%, 7/12; QuickNode 44.6% (548 submit errors), 5/8; Alchemy and Triton 0% (all 1,262 submit errors); cost per tx 8,177 lamports; score = 0.55×landing + 0.45×slot latency — [Helius benchmarks](https://www.helius.dev/benchmarks/sends). (Vendor-run; Triton/Alchemy zeros look like a configuration failure, not a landing result.)

#### Nozomi (Temporal)
- Endpoints: auto-routed `nozomi.temporal.xyz` (Cloudflare) and geo-DNS `edge.nozomi.temporal.xyz`; **direct** hosts `pit1`, `ewr1`, `ash1`, `lax1`, **`fra2`**, **`ams1`**, `lon1`, `tyo1`, `sgp1` `.nozomi.temporal.xyz` (http:// and https://), Cloudflare-proxied `fra`, `ams`, … (https only). Direct recommended for datacenter hosts; plain `http://` avoids per-request TLS cost — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Auth `?c=<API_KEY>`; no IP whitelisting; 401 = bad key — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Rate limit: per key, per region, per second; new keys default **5 req/s**; "Sending the same transaction to multiple regions does not count against a single region's limit"; increases granted in dashboard based on landing rate, success rate and "transaction quality" — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Delivery paths: Jito and Harmonic block builders plus Nozomi's own staked connections; "the tip is forwarded to the builder your transaction routes through"; bundles go only to builder paths, "submitted once per builder by default" — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Tip: default min 0.001 SOL, below-minimum txs "silently dropped: no error is returned"; bundles need ≥1 tipped member and never <1,001 lamports; 17 public tip addresses, rotate per tx; private addresses for high-volume clients; lower minimum negotiable; recommended CU price ≥1,000,000 micro-lamports — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Tip on failure: "the tip is an instruction inside the transaction, so if the transaction fails, the tip is never charged. However, a transaction that reverts on-chain after including the tip still pays it" — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Server-side retries against the recent blockhash until confirm/expiry; "client-side retry loops burn rate limit and lower priority"; "A high failure rate lowers your priority"; new keys have a warm-up period "because priority builds as landing rate is observed"; 429 can mean traffic flagged as spam — [Nozomi troubleshooting](https://use.temporal.xyz/nozomi/troubleshooting)
- Durable nonces accepted; "Block builders may deprioritize durable-nonce transactions because they're associated with spam"; benchmark with and without — [Nozomi troubleshooting](https://use.temporal.xyz/nozomi/troubleshooting)
- Dedup: for bundles, identical resubmission (same sigs, same order) returns 200 but is not redelivered; once any member confirms, pending copies are dropped and further submissions get 409; no dedup described for single txs — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- MEV-protect key available on request (whitelist of trusted validators, higher latency/expiry risk, "reduced, not eliminated") — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Tip stream: `https://api.nozomi.temporal.xyz/tip_floor`, `wss://api.nozomi.temporal.xyz/tip_stream`; live sample 2026-10-18T16:27Z: 25th 0.001, 50th 0.001, 75th 0.0011, 95th 0.01, 99th 0.02 SOL — [Nozomi tip_floor](https://api.nozomi.temporal.xyz/tip_floor)
- Pricing: no per-request or subscription price anywhere in the docs; cost is tip + CU price only — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Keep-alive: 65 s idle timeout, ping `/ping` every 60 s; "QUIC is not faster than a warm HTTP connection"; Batch Send < API v2 < JSON-RPC in overhead; Transaction v1 (SIMD-0296, 4,096-byte txs) accepted once gated — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)

#### Astralane (Iris sender; "Vortex" not found)

- Astralane also sells shreds ("Deshreds"), "Postpacks" fast tx feed — [Astralane llms.txt](https://astralane.gitbook.io/docs/llms.txt)

## Key question 1 — Benchmarks and same-slot landing for a mid-slot submission

### Takeaway
There is no independent, apples-to-apples 2025–2026 benchmark of the commercial senders; every number is vendor-run. The best-documented methodology (BlockRazor's durable-nonce race) measures "who reached the leader first", not same-slot landing. The only slot-granular public data (Helius benchmarks page) is for RPC providers and shows p50 ≈5 slots, p95 ≈7 slots at 200 ms slots for Helius's own path — far from same-slot. No source quantifies same-slot probability for a mid-slot submission.

### Cited Findings
- BlockRazor durable-nonce race (Aug 2025, vendor): same tx (0.001 SOL tip + 0.001 SOL priority fee) sent simultaneously to BlockRazor, bloXroute, 0slot, Temporal from servers in Frankfurt and New York, 1 tx per 1.6 s; Jito-route landings excluded; BlockRazor first-to-leader in 30.12% (FRA) / 39.83% (NY); competitor shares only in images; no sample size or dates — [BlockRazor](https://blockrazor.io/blog/20250801Benchmarking/)
- BlockRazor Frankfurt leaderboard (undated, 2026 page): BlockRazor > Temporal > Helius > Astralane > "Competitor #5" — [BlockRazor](https://blockrazor.io/chains/solana)
- Helius live benchmark (RPC providers, last 24 h, 6 regions, 1,251 samples/target, 8,177 lamports per tx): Helius 84.9% landed, slot p50 5 / p95 7; Chainstack 77.1%, 7/12; QuickNode 44.6%, 5/8; Alchemy, Triton 0% (submit errors) — [Helius benchmarks](https://www.helius.dev/benchmarks/sends)

Jito/Harmonic bundle paths realistically target the next leader slot.
- The sub-ms RTTs in the SDK README indicate that from a TeraSwitch-class Frankfurt host most sender ingress points are in the same metro; the race is decided by the sender's internal path to the leader, which no vendor publishes.

## Key question 3 — Tip floors and fee models

### Takeaway
Minimum tips cluster at 0.001 SOL (Nozomi, 0slot default, Astralane free tier, NextBlock default, bloXroute, Helius Max) with discounts for volume (Astralane 0.0001→0.00001 SOL; 0slot Advanced 0.0001; BlockRazor 0.0001; Helius SWQoS-only 0.000005; Jito 1,000 lamports). Tips are per-transaction except bundles, where one tipped member suffices (Jito, Helius, Nozomi) or every member tips (NextBlock). Only Harmonic uses priority fee as the tip. Tip is charged whenever the tx executes on-chain (even if it reverts) unless a revert-protected path is used.

### Cited Findings

- Tip-account write-lock contention: every vendor says rotate tip accounts; Astralane lets users check contention on public tip wallets; Nozomi/bloXroute offer private tip wallets — [Astralane](https://astralane.gitbook.io/docs/low-latency/send-txn-fee-tiers.md); [Nozomi](https://use.temporal.xyz/llms-full.txt); [bloXroute](https://docs.bloxroute.com/solana/trader-api/best-performance-for-landing-transactions)

### Inferences
- Jito's landed-tip median (~0.0000078 SOL) is 100× below the 0.001 SOL floors of the commercial senders; the commercial floors are a service price, not a market-clearing tip. Nozomi's 95th/99th (0.01/0.02 SOL) and NextBlock's sample 99th (0.48 SOL) show where competitive sniping flow actually bids.
- Because the floor is per landed-and-executed transaction, a pay-on-success design should route speculative buys through revert-protected paths (Jito bundleOnly, Harmonic, BlockRazor revertProtection, NextBlock revertOnFail) and accept their slower inclusion, or through un-protected SWQoS paths with slippage guards so a revert (and tip loss) is rare.

### Gaps
- Whether Helius, 0slot, BlockRazor, NextBlock or bloXroute charge anything when a tx never lands is undocumented (structurally they cannot, since the tip is an on-chain transfer, except Astralane Ghost).
- Exact ranking formula inside Helius's "priority tip buffer" and Nozomi's queue is not published.

## Key question 4 — "Land right behind this transaction" (backrun) semantics in 2026

### Takeaway
No public service offers a target-relative backrun ("place my tx immediately after signature X") on Solana in 2026. Jito's mempool-based backrun example is officially discontinued; the only ordering primitives are intra-bundle ordering (your own txs), `jitodontfront`/`dontfront` (top-of-bundle protection), BAM plugins (whitelist/application-level), and bloXroute's `submit-snipe` (two of your own competing txs). Snipers therefore race the creator's transaction rather than backrun it.

### Cited Findings
- Jito searcher-examples backrun: "Due to the deprecation of mempool features, support for this functionality has been discontinued" — [jito-labs/searcher-examples](https://github.com/jito-labs/searcher-examples)
- Jito bundles execute "sequentially and atomically", up to 5 txs, letting a searcher order only its own transactions — [Jito](https://docs.jito.wtf/lowlatencytxnsend/)
- `jitodontfront` must be at index 0 of a bundle; works on sendBundle and sendTransaction; Harmonic honours `dontfront`/`jitodontfront` bundle-control accounts — [Jito](https://docs.jito.wtf/lowlatencytxnsend/); [Harmonic FAQ](https://docs.harmonic.gg/reference/faq)
- RPC Fast advises adding "a jitodontfront-prefixed account to the first transaction to block back-running bundles" when sniping — [RPC Fast](https://rpcfast.com/blog/how-to-launches-snipe-pump)
- BAM plugins are "programmable interfaces to the BAM Nodes' scheduler" for custom sequencing (named: Maker Plugin); no backrun plugin is documented; DBI is whitelist-only — [bam.dev](https://bam.dev); [bam.dev docs](https://bam.dev/docs/bam/bam-overview/); [Solana Compass](https://solanacompass.com/news/jito-announces-bam-direct-bundle-ingest-routing-solana-bundles-past-the-block-engines-50ms-hop)
- Helius preconfirmations (`preconfSubscribe`) now on all paid plans with BAM and signer filters — a way to *observe* a BAM-scheduled tx early, not to order behind it — [Solana Compass](https://solanacompass.com/news/helius-opens-solana-preconfirmations-to-all-paid-plans-and-adds-four-new-filters)
- bloXroute `submit-snipe`: two of *your* competing txs (one via Jito, one via staked connections), not a target-relative backrun — [bloXroute](https://docs.bloxroute.com/solana/trader-api/api-endpoints/core-endpoints/submit-snipe); bloXroute "SnipeMe" docs page returns 404 — [bloXroute](https://docs.bloxroute.com/apis/mev-solution/snipeme)
- Astralane `sendIdeal` takes exactly 2 transactions; semantics undocumented — [ThorNode](https://docs.thornode.io/infrastructure/bifrost-api/endpoints/astralane)
- Harmonic: "Bundles are shared only with vetted, trusted block builders and never reach the public mempool"; leader filtering planned — [Harmonic bundles](https://docs.harmonic.gg/searchers/harmonic-bundles.md)
- Helius Alpenglow analysis: strategies that mirror TPU traffic or cancel/replace before optimistic confirmation lose their ~500–600 ms window (→ ~150 ms) — [Helius Alpenglow blog](https://www.helius.dev/blog/alpenglow)

### Inferences
- The pump.fun creation-slot game is a pure race against the creator's own bundle (creator + dev-buy) and other snipers; the only "behind the creator" guarantee available is to detect the create via shreds and submit fast enough that the leader's scheduler places you in the same block after it.
- Astralane's `sendIdeal` (exactly two txs) might be a creator-buy pairing primitive, but no documentation confirms this.

### Gaps
- Astralane `sendIdeal` and NextBlock `snipeTransaction` semantics are undocumented in public docs.
- Whether any BAM plugin exposes app-controlled backrun auctions to third parties: not found.

## Key question 5 — Durable nonces and simultaneous fan-out to many senders

### Takeaway
Fan-out of the same signed transaction to several senders is standard practice among sniper bots and is not documented as a ban trigger by any vendor; the chain dedups by signature so only one copy lands. However: block builders may deprioritise durable-nonce txs (Nozomi), BlockRazor's sandwich mode forbids nonces, Astralane lowers rebates for flow "shared with other RPCs or landing services" or using an advanced nonce, and every vendor warns that duplicate submissions to the *same* endpoint burn rate limit and priority.

### Cited Findings
- Nozomi: durable-nonce txs accepted; "Block builders may deprioritize durable-nonce transactions because they're associated with spam, so they can hurt landing on some paths (not always)"; "Don't benchmark two paths with the same durable nonce or identical signed transaction. Only one can land"; fan the same signed tx to multiple regions rather than duplicating on one endpoint; duplicates to one endpoint "burn your rate limit and lower your priority" — [Nozomi troubleshooting](https://use.temporal.xyz/nozomi/troubleshooting); [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- BlockRazor: "Don't use durable nonces in [sandwichMitigation] mode, because they make the protection ineffective" (fast mode has no such rule); BlockRazor's own benchmark used durable-nonce txs sent simultaneously to multiple providers — [BlockRazor](https://docs.blockrazor.io/transaction-submission/fast/solana/send-transaction); [BlockRazor benchmark](https://blockrazor.io/blog/20250801Benchmarking/)
- Astralane: higher rebate tiers for txs sent "without advanced nonce or broadcasting to other RPCs or landing services" — [Astralane](https://astralane.gitbook.io/docs/low-latency/submit-transactions/tip-refunds.md); `getNonce` API exists — [Astralane endpoints](https://astralane.gitbook.io/docs/low-latency/endpoints-and-configs.md)
- bloXroute explicitly suggests "using the same durable nonce so the first landing transaction invalidates the other" for its two-tx snipe and recommends sending to global + 1–2 regions in parallel — [bloXroute submit-snipe](https://docs.bloxroute.com/solana/trader-api/api-endpoints/core-endpoints/submit-snipe); [bloXroute best performance](https://docs.bloxroute.com/solana/trader-api/best-performance-for-landing-transactions)
- Harmonic: bundles cross-forwarded to all regions, send once — [Harmonic bundles](https://docs.harmonic.gg/searchers/harmonic-bundles.md); Nozomi bundles submitted once per builder, duplicates not redelivered, 409 after confirmation — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Helius: no dedup/ban text; `maxRetries: 0`, rebuild rather than resend — [Helius guide](https://www.helius.dev/docs/sending-transactions/guides/land-trades-with-sender.md); NextBlock: "Simply send us the transaction once", duplicate sigs within a bundle rejected — [NextBlock](https://docs.nextblock.io/llms-full.txt); Jito docs silent on duplicates/bans — [Jito](https://docs.jito.wtf/lowlatencytxnsend/)
- Durable-nonce semantics: a nonce is consumed once; of a set sharing one nonce "at most one of these transactions will be included and executed — and the fee will be collected only once" — [Helius sendTransaction docs via search](https://docs.helius.dev/docs/api-reference/rpc/http/sendtransaction.md)
- Practice: D3AD-E sniper sends each pre-signed buy to "all enabled providers at once" (Jito, Nozomi, 0slot, BlockRazor, NextBlock, Astralane, bloXroute, Helius Sender, …) and "A shared durable nonce means at most one copy lands" — [D3AD-E README](https://github.com/D3AD-E/Solana-sniper-bot); vvizardev's Rust adapter wraps Jito, Nozomi, ZeroSlot, bloXroute, NextBlock, BlockRazor, Astralane behind one interface — [vvizardev](https://github.com/vvizardev/solana-relayer-adapter-rust)
- NextBlock, Helius, 0slot, bloXroute examples all use recent blockhashes; none document a nonce prohibition — [NextBlock](https://docs.nextblock.io/llms-full.txt); [Helius](https://www.helius.dev/docs/sending-transactions/guides/land-trades-with-sender.md); [0slot](https://0slot.trade/docs.php)

### Inferences
- Nothing prevents sending one durable-nonce tx to every sender at once; the costs are (a) possible builder deprioritisation of nonce txs on Jito/Harmonic paths, (b) losing Astralane rebates, (c) key-reputation decay at Nozomi if most copies are "failed/expired" from its point of view. A blockhash-based tx fanned out identically has the same one-lands property (same signature) without the nonce stigma, as long as it is built after the create is seen.
- Nozomi's and Harmonic's reputation systems imply that fan-out should use *separate* keys per strategy so that the inevitable "lost race" copies do not drag down the key used for protected flow.

### Gaps
- No vendor publishes a written ban policy for cross-provider fan-out; the only penalty found is Astralane's rebate tiering.
- 0slot's durable-nonce cookbook page could not be fetched.

## Key question 6 — What experienced pump.fun sniper developers say works and warn against

### Takeaway
Public 2025–2026 practitioner material converges on: shred-level detection (Jito ShredStream until Sep 2026, now DoubleZero Edge / vendor shred feeds), pre-built pre-signed transactions, fan-out to many senders from a co-located Frankfurt/Amsterdam/NY host, dynamic tips from tip-floor streams, strict slippage, and never relying on a single path. Warnings: public RPC, WebSocket program subscriptions, hard-coded tips, cloud regions without colocation, sending bundles unsimulated, and the scam-bot infestation of sniper repo issue trackers.

### Cited Findings
- D3AD-E/Solana-sniper-bot (open source, 2026): reads creates from Jito ShredStream at shred level, "<1 ms" build/send, pre-signed tx sent to all enabled providers with a shared durable nonce; INFRA.md: FRA/AMS/NYC recommended, avoid Chicago/Dallas/LA/Sydney/São Paulo; `net.core.rmem_max=128MB` "most valuable sysctl", `tcp_slow_start_after_idle=0`, `isolcpus`/`nohz_full`, SCHED_FIFO pinning, run on host not Docker, ECS-capable DNS (8.8.8.8), avoid 1.1.1.1/VPN; internal detect-to-wire ≈26 µs, signing 11.3 µs; one spinning core per provider; watch `never_landed` (tips/CU too low), `skipped_no_nonce`, `send_errors`; use ghost/test modes before live — [README](https://github.com/D3AD-E/Solana-sniper-bot); [INFRA.md](https://raw.githubusercontent.com/D3AD-E/Solana-sniper-bot/main/INFRA.md)
- RPC Fast guide (vendor): Yellowstone gRPC account-write filters (5–20 ms vs 150–300 ms for WS program subs); multi-relay to all Jito regions + Astralane + Lil' JIT in parallel; dynamic tips from last 50 blocks; `jitodontfront` on first tx; simulate before paid bundle submission ("a failed bundle still pays the tip"); avoid public RPC (150–600 ms, 2–5 slots stale), hardcoded tips, single cloud region, no SWQoS; co-locate in Frankfurt + Ashburn; cross-region adds 80–150 ms — [RPC Fast](https://rpcfast.com/blog/how-to-launches-snipe-pump)
- Chainstack pump-fun-bot maintainers warn their Issues section "is often targeted by scam bots that try to redirect users to external resources and drain funds" — [Chainstack docs](https://docs.chainstack.com/docs/solana-creating-a-pumpfun-bot.md)
- Vendor claim: "200+ competing bots within the first 500 milliseconds of a pump.fun launch" — [search summary, rpcfast/solanatools](https://rpcfast.com/blog/top-solana-sniper-bot)
- Nozomi: strict slippage and `minAmountOut` regardless of key type; MEV-protect keys are slower; client retries counterproductive — [Nozomi docs](https://use.temporal.xyz/llms-full.txt)
- Triton: `maxRetries: 0`, `skipPreflight: true`, simulate separately — [Triton advice](https://docs.triton.one/chains/solana/cascade/transaction-sending-advice)
- Helius: price CU via `getPriorityFeeEstimate` on the touched accounts, don't hardcode; keep connections warm (>5 s idle → ping) — [Helius guide](https://www.helius.dev/docs/sending-transactions/guides/land-trades-with-sender.md)
- Post-Alpenglow guidance for senders: replace tick-based "how far into the slot" logic with a local slot clock; gate Alpenglow logic on `getAgGenesisCert`; buffer Geyser data per (slot, bank_id); move from `confirmed` to `finalized` only after activation — [solana.com](https://solana.com/upgrades/alpenglow)
- BlockRazor's Feb-2026 analysis argues "over-reliance on one block-building path carries risk, so diversifying submission routes may be prudent" — [BlockRazor blog](https://www.blockrazor.io/blog/20260206solanaBlockConstruction/)
- The dev.to "fastest way" article is a promo for AllenHark Slipstream (author founder); its "~65% of slots Jito" and latency ranges are unsourced — [dev.to](https://dev.to/techmystique_/the-fastest-way-to-land-solana-transactions-in-2026-5gg9)

### Inferences
- The consensus architecture among practitioners is exactly the one the user is building: shred/Geyser detection in Frankfurt, pre-signed tx, parallel fan-out to 6–9 senders with one-lands semantics, and a kill-switch on `never_landed`/`send_errors` counters.
- Because Jito ShredStream is reportedly gone since 5 Sep 2026, detection feeds now come from DoubleZero Edge, Astralane Deshreds/Postpacks, BlockRazor Shred Stream, NextBlock TX Stream (5 SOL/31 days) or a self-run validator; this is a separate purchasing decision from the sender.

### Gaps
- I found no X/Twitter threads or Discord summaries with first-hand, dated landing-rate comparisons of 0slot vs Nozomi vs Jito for pump.fun creation-slot snipes; everything is vendor or repo-README level.
- No independent confirmation of Jito's ShredStream shutdown date beyond a competitor blog and a sniper README.
