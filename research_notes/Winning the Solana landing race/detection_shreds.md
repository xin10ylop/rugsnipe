# Detecting a pump.fun create inside the leader's slot: shred feeds, decoding, timing, and what Alpenglow changes

Research date: 2026-10-18. Two facts change the premise of the question and should be read first:

1. **Slots are 200 ms, not 400 ms.** SIMD-0525's last step (200 ms) activated on mainnet at epoch 1053 on 9 Oct 2026; the three earlier steps (350/300/250 ms) each ran 15–19 ms slower than target in practice. — [Solana Compass](https://solanacompass.com/news/solanas-200ms-slot-time-is-live-on-mainnet-at-epoch-1053-completing-simd-0525); [solana.com/upgrades/alpenglow](https://solana.com/upgrades/alpenglow)
2. **Jito ShredStream no longer exists.** Jito shut it down on 5 Sept 2026 and told users to migrate to DoubleZero Edge. — [Jito docs](https://docs.jito.wtf/lowlatencytxnfeed/); [Solana Compass](https://solanacompass.com/news/doublezero-removes-unauthorized-shred-retransmitters-claims-70-plus-lead-over-all-competitors)

Everything below is written for a non-validator trading box in Frankfurt (FRA) or Amsterdam (AMS). "Vendor claim" means the number was published by the party selling the product and no independent measurement was found.

## Key question 1: From leader execution to first shred, and when a Frankfurt box can see it via (a) Turbine, (b) a shred relay, (c) Yellowstone gRPC at `processed`

### Takeaway
On Agave the leader does not shred a transaction the instant it executes: entries are coalesced for up to 50 ms (or until ~2 "typical" erasure batches of bytes accumulate, or the slot ends) and then padded into a 32-data + 32-coding FEC set and dispatched at once. After that, the best commercial shred relays in Frankfurt differ from each other by single-digit milliseconds at p50 (vendor-run benchmarks), shred-native feeds beat Yellowstone gRPC `processed` by roughly 5–11 ms median and 17–50 ms at p95/p99 (vendor-run), and plain RPC WebSockets are hundreds of ms to seconds behind. No independent, published distribution of "first shred arrival vs. slot start" for a Frankfurt observer was found.

### Cited Findings

**Leader side (primary source: Agave code, current master)**
- The broadcast stage coalesces entries before shredding: `const ENTRY_COALESCE_DURATION: Duration = Duration::from_millis(50)`, measured from when coalescing began. Coalescing also stops when the slot ends (`last_tick_height >= max_tick_height`), when the batch reaches `2 * get_data_shred_bytes_per_batch_typical()` bytes ("Empirically discovered to be a good balance between avoiding padding and not delaying broadcast"), when the batch is within 5 % of tightly packing erasure batches ("Just send it"), or when a SlotStart/Marker boundary arrives. — [agave turbine/src/broadcast_stage/broadcast_utils.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/turbine/src/broadcast_stage/broadcast_utils.rs)
- Once a component (entry batch) is received it is shredded and dispatched immediately; "Data and coding shreds are sent in a single batch." The code does not wait for slot end. The index-0 data shred is inserted into blockstore synchronously before transmission (duplicate-block safety). — [agave standard_broadcast_run.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/turbine/src/broadcast_stage/standard_broadcast_run.rs)
- Every FEC set is exactly 32 data + 32 coding shreds; the final partial set is padded with empty data shreds (`.chain(std::iter::repeat(&[][..])).take(DATA_SHREDS_PER_FEC_BLOCK)`), so a small entry batch still costs a full 64-shred set. The `DATA_COMPLETE_SHRED` (or `LAST_SHRED_IN_SLOT`) flag is set only on the last data shred of the whole serialized batch. — [agave ledger/src/shred/merkle.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/ledger/src/shred/merkle.rs)
- Shred constants: `DATA_SHREDS_PER_FEC_BLOCK = 32`, `CODING_SHREDS_PER_FEC_BLOCK = 32`, common header 83 bytes, data headers 88 bytes, coding headers 89 bytes; `fec_set_index` steps by 32 within a slot; flags `SHRED_TICK_REFERENCE_MASK 0b0011_1111`, `DATA_COMPLETE_SHRED 0b0100_0000`, `LAST_SHRED_IN_SLOT 0b1100_0000`; only Merkle variants exist (0x6_/0x7_ code, 0x9_/0xb_ data; proof_size 6 for 32:32). The signature covers the Merkle root of the erasure batch, not each shred. — [agave ledger/src/shred.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/ledger/src/shred.rs)
- Shreds are ~1,228 bytes (one UDP datagram). — [OrbitFlare](https://orbitflare.com/blog/fundamentals/shredstream); [Helius](https://www.helius.dev/blog/solana-shreds)

**Earlier than shreds: pre-shred "preconfirmation" feeds**

### Inferences
- Leader-side budget: a pump.fun create executed at time t inside the slot will leave the leader as shreds somewhere between "a few ms" and ~50 ms later on Agave, depending on how fast the coalescing byte target fills (busy slots fill faster, so the coalesce timeout rarely binds at high TPS; quiet slots pay the full 50 ms). Jito-Agave inherits this code unless patched; Firedancer's equivalent is undocumented (gap).
- Relay-side budget for a well-placed FRA box with a top-tier feed: a few ms after the first validators have the shred (the vendor races above put the best feeds within ~2–7 ms p50 of each other, with p99 tails of 25–55 ms).
- Yellowstone `processed` adds roughly 5–11 ms median and 17–50 ms p95/p99 on top of a shred-native feed in Frankfurt (vendor-run but consistent across RPC Fast, Shreder and Helius's "8 ms" claim).
- Rough stack for a 200 ms slot on an Agave leader, best case: execute → +5…50 ms shredded → +2…10 ms at a FRA relay subscriber → +≤1 ms decode (microbenchmarks claim µs-level) → tx build/sign (sub-ms) → send to leader. If the leader is itself in FRA/AMS (≈ half of slots), the submit hop is ~1 ms; via Jito Block Engine it was ~50 ms (see KQ4). The detection path therefore leaves roughly 100–180 ms of a 200 ms slot in the best case and can leave almost nothing if the create landed late in the slot.
- Preconfirmation feeds are the only route that beats the 50 ms coalesce window, but coverage is partial (only Helius-forwarding or BAM leaders).

### Gaps
- No independent measurement of absolute "slot start → first shred at Frankfurt" latency was found; every ms figure above is a relative race between two feeds published by one of the vendors.
- The actual value of `get_data_shred_bytes_per_batch_typical()` (bytes that trigger early dispatch) was not located in the fetched source.
- Firedancer's shred-emission cadence (microblock → shred timing) is undocumented in the sources reached.
- DoubleZero's live scoreboard (data.doublezero.xyz) is JavaScript-rendered and could not be read; Triton's cited May 2026 analysis that DoubleZero multicast "won ~90 % of slots" could not be located as a primary document.

## Key question 2: Can an entry be decoded before the FEC set completes, and what do open-source decoders actually do?

### Takeaway
Yes. Entries are deserialized from data shreds only, in index order, from the shred after the previous `DATA_COMPLETE_SHRED` through the next one; coding shreds are used only to recover missing data shreds. Agave's blockstore, Jito's shredstream-proxy deshredder and the 0xfnzero SDK all emit entries per data-complete range as soon as every data shred in that range is present, regardless of whether the 32 coding shreds (or the padding data shreds after the flag) have arrived. The catch is that on Agave the flag sits only on the last data shred of a coalesced batch, so you still need the whole batch's data shreds, which is normally most of one FEC set.

### Cited Findings
- Agave read path: `get_slot_entries_in_block` / `get_entries_in_data_block` read only `data_shred_cf` in index order and call `Shredder::deshred` on each completed range; "The ranges represent data shred indices that can reconstruct a block component… the data shred at index completed_ranges[i].end - 1 has DATA_COMPLETE_SHRED flag." A completed range is emitted only when `received_data_shreds.contains_range(...)` is true for it. A missing shred returns `MissingShred`; coding shreds are never touched on the read path. Recovery (`try_shred_recovery`) runs only when `(#data + #coding shreds) > erasure.num_data` for that set. — [agave ledger/src/blockstore.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/ledger/src/blockstore.rs)
- `Shredder::deshred` requires strictly consecutive indices (else `TooFewDataShards`), the last shred must carry `DATA_COMPLETE_SHRED`, and "No trailing shreds if we have already observed DATA_COMPLETE_SHRED." Concatenated data is deserialized to `Vec<Entry>`. — [agave ledger/src/shredder.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/ledger/src/shredder.rs)
- Flag placement: Agave sets `DATA_COMPLETE_SHRED` (or `LAST_SHRED_IN_SLOT`) only on the last data shred of the whole serialized batch, which may be a padding shred. — [agave ledger/src/shred/merkle.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/ledger/src/shred/merkle.rs)
- Jito shredstream-proxy `deshred.rs`: groups shreds by `(slot, fec_set_index)`; recovery is attempted when a set holds at least `num_data_shreds` shreds (from a coding shred header, or `index - fec_set_index + 1` from a flagged data shred) and not all data shreds are present, using `solana_ledger::shred::merkle::recover`. Deshredding is a separate pass that fires whenever a complete range exists: "A segment ends at the first `DataComplete` at or after `index`"; output is `(slot, entries, payload)` per DATA_COMPLETE range, which can span several FEC sets; "We allow `Unknown` towards the left since sometimes entire FEC sets are not sent out." State evicted at `SLOT_LOOKBACK = 50` slots; no wall-clock timers. The proxy also had a raw-UDP forward mode and a gRPC deshred mode. Jito's service is dead but the code is Apache-2.0 and still the reference receiver named by Everstake and Helius. — [jito-labs/shredstream-proxy deshred.rs](https://github.com/jito-labs/shredstream-proxy/blob/master/proxy/src/deshred.rs); [Jito docs](https://docs.jito.wtf/lowlatencytxnfeed/); [Everstake docs](https://docs.blockspace.everstake.com/shredstream)
- 0xfnzero `sol-shred-sdk` (Rust, v4.0.5 on 18 Oct 2026, MIT): pipeline "UDP packet -> Solana/Agave Shred -> FEC recovery -> deshred -> Entry -> VersionedTransaction -> event parser"; FEC recovery starts only after ≥ `num_data_shreds` distinct shards; raw-UDP mode does not verify leader signatures (no leader schedule); typed parsers for PumpFun create/create_v2, Mayhem, PumpSwap, Raydium, Meteora, Orca; local microbenchmark 3.28 M packets/s; README explicitly says its benchmarks do not measure production latency. Companion `solana-streamer` (187 stars) wraps Yellowstone gRPC and ShredStream. — [sol-shred-sdk](https://github.com/0xfnzero/sol-shred-sdk); [docs.rs](https://docs.rs/sol-shred-sdk); [GitHub search](https://github.com/0xfnzero/solana-streamer)
- Other reference receivers: Triton `rpcpool/deshred-example` ("reassembles incoming shreds into transactions"); BlockRazor `shreds-subscribe`; a small `shredstream-decode-example` repo (OrbitFlare-oriented, Reed-Solomon + pump.fun parsing). — [Triton docs](https://docs.triton.one/chains/solana/shred-streaming); [BlockRazor docs](https://docs.blockrazor.io/streams/block-stream/solana/shred-stream); [GitHub](https://github.com/rutledgeearly815/shredstream-decode-example)
- Shreds carry only transaction-visible data: no logs, balance changes or execution status come from shreds alone. — [sol-shred-sdk README](https://github.com/0xfnzero/sol-shred-sdk); [Shyft](https://wp-origin.shyft.to/?p=1782)
- Pre-Alpenglow blocks also contain tick entries and vote transactions inside the same entry batches; both disappear after Alpenglow (see KQ5). — [solana.com/upgrades/alpenglow](https://solana.com/upgrades/alpenglow)

### Inferences
- The practical decode trigger is "all data shreds from previous flag+1 through the flagged shred received", not "FEC set complete". Because the flag is on the batch's last data shred, you normally wait for most of the data shreds in the current set; the 32 coding shreds and any padding shreds after the flag are irrelevant unless something was lost. With a 50 ms coalesce window this means the create and everything coalesced with it arrive as one unit.
- An aggressive decoder could speculatively parse individual data shreds: entries are bincode/wincode-serialized `Vec<Entry>` and transactions inside them are length-prefixed, so a transaction wholly contained in one shred's payload can in principle be extracted before the range is complete. No open-source decoder found does this; it would be custom work and gives at most the intra-batch arrival spread (sub-ms to a few ms) rather than tens of ms.
- Raw-UDP feeds from vendors other than your own validator cannot be signature-verified without the leader schedule; the SDKs skip verification, which is an accepted risk for a trading signal but means a malicious or buggy relay could feed fake creates.

### Gaps
- No source documents Firedancer's deshredding/replay granularity for comparison.
- No published measurement of how often a pump.fun create's batch is "data-complete" within one FEC set vs. spanning several.

## Key question 3: How do leading pump.fun sniper bots (open-source and commercial, 2025–2026) detect creates, and what time-to-detect do they report?

### Takeaway
Open-source bots overwhelmingly use Yellowstone gRPC (transaction/account subscriptions on the pump.fun program), with the 0xfnzero Rust SDK family being the only widely-used open code that ingests raw shreds; commercial Telegram/web snipers do not disclose their detection method and publish no time-to-detect figures. The only quantified "same-block" evidence is on-chain: Pine Analytics found >50 % of pump.fun tokens are bought in their creation block, largely by deployer-linked wallets that can only be there via pre-signed/bundled transactions or shared infrastructure, not by detection.

### Cited Findings
- Frontrunx `solana-pumpfunx-sniper-bot` (Rust) tracks create/buy on pump.fun and migration events using Yellowstone gRPC; `bitman09/pumpfun-sniper-bot` (TypeScript) uses a Geyser WebSocket feed. — [GitHub](https://github.com/Frontrunx/solana-pumpfunx-sniper-bot); [ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fbitman09%2Fpumpfun-sniper-bot)
- GetBlock's pump.fun guide subscribes to pump.fun program transactions over Yellowstone and filters for the create instruction. — [GetBlock](https://docs.getblock.io/guides/how-to-track-pump.fun-token-mints-with-getblocks-yellowstone-grpc.md)
- 0xfnzero's `sol-trade-sdk` (350 stars) / `solana-streamer` (187 stars) / `sol-shred-sdk` are the main open Rust stack combining shred or gRPC ingestion with pump.fun parsing and Jito/SWQoS submit lanes; a GitHub repo search for "pumpfun shred" returns 94 repos, almost all from this author or derivative. — [GitHub search results](https://github.com/0xfnzero/sol-trade-sdk)
- Vendor sniper guides (RPC Fast, OrbitFlare) describe the stack as "Shredstream-fed hot path + gRPC for structured data", quote 5–15 ms median notification latency for gRPC/shred feeds vs WebSockets, and say shreds give "50–200 ms of forward visibility". Vendor claims, no methodology; the recurring "90 % of DIY bots fail" statistic has no primary source. — [RPC Fast](https://rpcfast.com/blog/how-to-launches-snipe-pump); [OrbitFlare](https://orbitflare.com/blog/developers/solana-sniper-bot-guide); [RPC Fast stack guide](https://rpcfast.com/blog/complete-stack-competitive-solana-sniper-bots)
- MadeOnSol's sniper ranking (updated 18 Oct 2026) lists Trojan, MevX, Soul Sniper, SolSniper, Sniperoo, BonkBot, SolBundler, Telemetry etc.; none state a detection method; the only quantified claim is Telemetry's "sub-millisecond trade execution" (unsupported) and SolBundler's "lands buys in block 0 via Jito bundles" (i.e. the sniper is the deployer). — [MadeOnSol](https://madeonsol.com/best/snipers)
- Pine Analytics (21 Apr 2025, data 15 Mar–Apr 2025, possibly outdated): "over 50% of tokens are now sniped in the exact block" of creation; deployer-funded same-block snipes were ~1.75 % of launches, 15,000+ tokens/month, 4,600+ sniper wallets, 87 % profitable, >55 % fully exited within one minute; same-block participation "typically requires pre-signed transactions, off-chain coordination, or shared infrastructure between deployer and buyer." — [Pine Analytics](https://pineanalytics.substack.com/p/exit-liquidity-machines)
- PumpPortal's WebSocket feed: no latency data located in any source. — gap, see below.
- Helius markets Preconfirmations + "Sender Max" (0.001 SOL minimum tip) explicitly for acting on a detected transaction before it lands. — [Helius preconf overview](https://www.helius.dev/docs/pre-confirmations/overview)

### Inferences
- "Same-block snipes" in the on-chain data are dominated by bundle-mates of the creator, not by independent detectors; genuinely detecting a create inside the leader's slot and landing in that slot is not something any open-source bot demonstrates or any vendor measures.
- The open-source frontier for independent same-slot detection is the 0xfnzero raw-shred path plus a BAM/DBI or Helius Sender Max submit lane; commercial Telegram bots are almost certainly on gRPC/LaserStream-class feeds given their multi-second UX.

### Gaps
- No bot, open or commercial, publishes a measured time-to-detect for pump.fun creates.
- PumpPortal (and similar aggregator WebSockets) have no published latency.
- No 2026 refresh of the Pine Analytics same-block study was found.

## Key question 4: How long does a leader keep accepting transactions into the current slot, and is same-slot inclusion after mid-slot detection realistic on Agave, Jito-Agave, Firedancer and BAM leaders?

### Takeaway
An Agave leader records transactions into the working bank until PoH reaches `max_tick_height` (the end of the slot); there is no earlier cutoff, so a transaction that reaches the leader with enough ticks left can be recorded in the same slot. With 200 ms slots and leaders holding 4 slots (~800 ms), the realistic window after a mid-slot detection is tens of milliseconds, and it depends heavily on the submit path: BAM's Block Engine hop was ~50 ms (Jito's own figure, now bypassed by Direct Bundle Ingest for whitelisted searchers), BAM auction rounds are 20 ms, and Firedancer's pack-stage cutoff is undocumented.

### Cited Findings
- Agave PoH recorder: a working bank is installed with `min_tick_height = bank.tick_height()` and `max_tick_height = bank.max_tick_height()`; "recorded entry must be >= WorkingBank::min_tick_height && entry must be < WorkingBank::max_tick_height"; `record()` returns `MaxHeightReached` once the bank is cleared at max height; the bank is cleared when `tick_height >= max_tick_height`. Leader window: `leader_first_tick_height = first_slot * ticks_per_slot + 1`, `last_tick_height = (last_slot + 1) * ticks_per_slot`; grace ticks `min(ticks_per_slot * MAX_GRACE_SLOTS, ticks_per_slot * num_slots / GRACE_TICKS_FACTOR)` with `GRACE_TICKS_FACTOR = 2`, `MAX_GRACE_SLOTS = 2`. For Alpenglow a footer is sent at `max_tick_height - 1` after waiting for the bank to freeze (timeout `ns_per_slot`). `ticks_per_slot` is bank-configured (64 appears only in a comment). — [agave poh/src/poh_recorder.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/poh/src/poh_recorder.rs)
- Agave banking stage: leaders "process all buffered transactions without forwarding them"; unschedulable transactions go back to the buffer when retryable, expire by age, buffer holds up to 100,000 packets; `SLOT_BOUNDARY_CHECK_PERIOD` 10 ms; consumer batches of 64 tx; 4 workers default (max 64); a validator 2 slots before its leader slot starts holding packets instead of forwarding. — [Agave banking-stage API doc (unofficial mirror)](https://mintlify.wiki/anza-xyz/agave/api/banking-stage); [Helius v1.18 notes](https://docs.helius.dev/blog/all-you-need-to-know-about-solanas-v1-18-update)
- Agave 4.0 removed UDP TPU ingestion; QUIC is the only ingress. Forwarding to upcoming leaders still exists via `tpu-client-next` (v2.3+). — [Anza 4.0 patch notes](https://www.anza.xyz/blog/agave-4.0-patch-notes); [Helius v2.3 notes](https://www.helius.dev/blog/agave-v23-update--all-you-need-to-know)
- Slot/leader timing after SIMD-0525: 200 ms slots since epoch 1053 (9 Oct 2026); each leader's 4-slot turn is ~800 ms; per-slot limits scale with slot time so blocks hold half the capacity; earlier stages overshot target by 15–19 ms. — [Solana Compass](https://solanacompass.com/news/solanas-200ms-slot-time-is-live-on-mainnet-at-epoch-1053-completing-simd-0525)
- BAM (Jito): transactions go first to a BAM node (QUIC or via Block Engine), are filtered/ordered in an AMD SEV-SNP TEE, and forwarded as ordered microblocks to the BAM validator, which executes "in strict FIFO order without reordering." BAM covered 385 validators / 164 M SOL / 37 % of stake at epoch 1050; auction rounds tightened from 25 ms to 20 ms with 200 ms slots. — [bam.dev](https://bam.dev/overview); [Solana Compass](https://solanacompass.com/news/jito-details-bams-alpenglow-plan-maintenance-mode-for-all-mainnet-nodes-no-firebam-during-the-transition)
- Jito says the Block Engine "added an extra hop of roughly 50ms" (≈ a quarter of a 200 ms slot); Direct Bundle Ingest (announced 13 Oct 2026, whitelisted early cohort live for a month) lets searchers submit bundles straight to BAM nodes over QUIC/JSON-RPC, skipping the Block Engine's 50 ms auction; Jito reports land rate 0.45 % → 0.57 % and simulation success 11.4 % → 16.1 % after the change (own before/after, confounded by filtering changes). DBI is unavailable while BAM is in Maintenance Mode around Alpenglow. — [Solana Compass](https://solanacompass.com/news/jito-announces-bam-direct-bundle-ingest-routing-solana-bundles-past-the-block-engines-50ms-hop)
- Firedancer pack: schedules by reward-to-compute into microblocks "until microblock full or no schedulable transactions", bundles of 1–5 tx (`FD_PACK_MAX_TXN_PER_BUNDLE = 5`) execute atomically; the mirrored docs give no slot-end cutoff or microblock cadence. — [Firedancer block-packing (unofficial mirror)](https://mintlify.wiki/firedancer-io/firedancer/internals/block-packing)
- Firedancer/Frankendancer/FireBAM are not supported during the Alpenglow migration (operators told to run Agave 4.3.x-based clients: Agave, Jito-Solana, Harmonic Salsa); ~15.8 % of stake was on Firedancer-family labels. — [solana.com/upgrades/alpenglow](https://solana.com/upgrades/alpenglow); [Solana Compass](https://solanacompass.com/news/anza-sets-alpenglow-mainnet-date-solanas-consensus-switch-is-scheduled-for-october-21-at-about-1450-utc)
- Glassnode: QUIC handshake to a colocated validator measured at 0.965 ms (Chicago); Jito block engines in Amsterdam, Frankfurt, London, Dublin, NY, SLC, Tokyo, Singapore; BAM latency "assumed to match the block engine's". — [Glassnode](https://latency.glassnode.com/solana/about)
- RPC Fast's own landing benchmark: Beam (3 relays) averaged 330 ms submit→land vs 457 ms for standard RPC, p90 589 vs 1,065 ms, at most 1 slot vs up to 4 slots (vendor, 20 runs; pre-200 ms-slot). — [RPC Fast benchmarks](https://rpcfast.com/benchmarks)

### Inferences
- Same-slot inclusion is mechanically allowed on Agave/Jito-Agave up to the final tick; nothing in the code closes the bank early. The constraint is purely latency: detection (≥5–50 ms leader coalesce + ~2–10 ms relay) + build + transit to the leader + the leader's scheduler queue + PoH record, all inside what remains of a ~200 ms (really ~215–220 ms) slot.
- Worked example: create executed at 30 ms into the slot → shredded by ~40–80 ms → at FRA box by ~45–90 ms → tx sent by ~50–95 ms. To a FRA/AMS leader via direct QUIC/TPU (≈1–5 ms) or DBI this leaves ~100+ ms; via the legacy Block Engine (~50 ms hop + 20 ms auction round) it leaves ~30–50 ms, which is marginal. If the create executed in the second half of the slot, same-slot is unrealistic on any path and the realistic target is the next slot of the same 4-slot leader.
- Because a 4-slot leader window is only ~800 ms, "same leader, next slot" is the robust fallback and keeps the submit path (same TPU/BAM node) unchanged; this matters more than squeezing the last ms out of detection.
- Jito-Agave vs Agave: identical PoH/banking semantics; the difference is the BAM ordering layer (FIFO as sequenced by the BAM node, 20 ms rounds), which adds queueing but no earlier cutoff. Firedancer: unknown cutoff (gap), and irrelevant during the Alpenglow transition since it is not allowed to run.

### Gaps
- No source quantifies how late in a slot an Agave or BAM leader actually records the last externally-received transaction (an empirical "last-tx-offset" distribution would settle this).
- Firedancer's pack-stage slot-end behaviour and FIFO/queue latency inside BAM nodes are undocumented.
- DBI access is whitelisted; terms and latency were not published.

## Key question 5: What Alpenglow (Votor now, Rotor later) changes for shred propagation, shred formats, shred-stream vendors, and what Jito/Triton/Helius/DoubleZero have announced

### Takeaway
What activates at epoch 1064 on 21 Oct 2026 is Votor only: off-chain BLS votes, ~150 ms finality, `confirmed == finalized`, tick entries and vote transactions removed from blocks, multiple candidate banks per slot tagged by `bank_id`. Turbine, the shred wire format and every shred feed stay exactly as they are ("Initially we stay with Turbine"). Rotor (single-hop stake-weighted relays, one unified erasure-coded shred type, multicast-friendly) is deferred to a separate, unscheduled SIMD; when it lands, propagation is expected to get faster and vendors will have to change their decoders, but non-validators are not addressed in any published text.

### Cited Findings
**Activation and scope**
- Mainnet activation at epoch 1064, Wed 21 Oct 2026 (~14:50–15:00 UTC); feature gate flips at the epoch start, TowerBFT keeps running for 5,000 slots (~18 min), Alpenglow takes over at slot 459,653,000; Votor ships in Agave 4.3 (v4.3.2 recommended), fast leader handoff in 4.4; devnet activated 25 Sept 2026. — [solana.com/upgrades/alpenglow](https://solana.com/upgrades/alpenglow); [Solana Compass](https://solanacompass.com/news/anza-sets-alpenglow-mainnet-date-solanas-consensus-switch-is-scheduled-for-october-21-at-about-1450-utc); [Solana Compass (4.3.2)](https://solanacompass.com/news/anza-names-agave-v432-the-recommended-release-for-all-solana-validators-five-days-before-alpenglow)
- SIMD-0326 excludes Rotor: "Rotor will be introduced later and will get its own SIMD"; "Initially we stay with Turbine as the data dissemination protocol"; the only terminology change is that "A slice was formerly called FEC-set." No shred format change, no slot-duration change, no statement on non-voting nodes. — [SIMD-0326](https://raw.githubusercontent.com/solana-foundation/solana-improvement-documents/main/proposals/0326-alpenglow.md)
- Anza's Alpenglow page lists Rotor under "What's coming next" with no date. — [anza.xyz/alpenglow](https://anza.xyz/alpenglow)

**What changes in the data stream now (relevant to shred decoders)**
- Vote transactions leave blocks; PoH no longer paces blocks so leaders stop emitting tick entries ("Code that infers position within a slot from tick counts will break… Keep a local slot clock that corrects for latency to the leader, rather than timing from first-shred arrival"); `Clock.unix_timestamp` is set by the leader within bounds; a slot can have multiple banks tagged `bank_id` (Agave 4.3; expected in <1 % of slots once fast leader handoff ships in 4.4); Yellowstone `v16.0.0-rc10+solana.4.3.0` has built-in buffering; legacy Geyser callbacks deprecated; `confirmed` and `finalized` become equivalent and `confirmed` is later removed; JSON-RPC/WebSocket unchanged; "Pre-confirmation streaming (such as processed notifications) sees the same data at the same pipeline point." `getAgGenesisCert` returns null until migrated. — [solana.com/upgrades/alpenglow](https://solana.com/upgrades/alpenglow)
- Block footer at `max_tick_height - 1` carrying the latest certificate; block markers/headers exist in the shred stream and are skipped by entry readers ("Block markers are skipped because they do not contain entries"). — [agave poh_recorder.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/poh/src/poh_recorder.rs); [agave blockstore.rs](https://raw.githubusercontent.com/anza-xyz/agave/master/ledger/src/blockstore.rs)
- Votor finality: one round at 80 % stake (~100 ms) or two rounds at 60 % (~150 ms); simulation: 65 % of stake finalizes within 50 ms of raw network latency; with a ~70 ms longest hop fast path ≈120–150 ms; "an expectation, not a constant". — [Helius Alpenglow](https://www.helius.dev/blog/alpenglow); [Alchemy](https://alchemy.com/blog/solana-alpenglow); [solana.com](https://solana.com/upgrades/alpenglow)

**Rotor design (future)**
- Single-hop: leader splits each block into slices, erasure-codes each slice into shreds, builds a Merkle tree and signs the root; each shred goes to one relay which broadcasts it to all nodes, "with the next leader receiving it first"; relays are stake-weighted sampled so transmit load is proportional to stake; "Rotor sends one erasure-coded version of each shred. Turbine's separate data and recovery shreds are gone, though the redundancy ratio is unchanged"; "compatible with multicast systems such as DoubleZero". Whitepaper figures: 1,500 shreds at 1 Gb/s take ~18 ms; ~150 nodes reach 80 % of stake in ~2 ms. Blokstor accepts a shred only if the leader signature and Merkle path validate and emits a block event when the first complete block arrives. — [Helius Alpenglow](https://www.helius.dev/blog/alpenglow); [Alchemy](https://alchemy.com/blog/solana-alpenglow)
- Secondary sources conflict on relay selection (randomized stake-proportional sampling vs deterministic assignment); the whitepaper itself (anza.xyz/alpenglow-1-1) could not be fetched. — [Figment](https://www.figment.io/insights/alpenglow-solanas-new-consensus-protocol-built-for-real-time-blockchains/); [Everstake](https://everstake.one/blog/what-is-alpenglow-in-solana); [Substack summary](https://davidekete.substack.com/p/introducing-alpenglow-solanas-new)
- Helius: "Turbine will be replaced by Rotor once Alpenglow is implemented. Stake will still influence which peers validators broadcast to under Rotor." — [Helius shreds blog](https://www.helius.dev/blog/solana-shreds)

**Vendor/ecosystem announcements**
- Jito: ShredStream shut down 5 Sept 2026 (replacement: DoubleZero Edge). BAM: all mainnet BAM nodes enter Maintenance Mode in the days before activation (MPP and DBI unavailable, validators revert to ordinary Jito-Agave Block Engine mode, bundles keep working); FireBAM/FrankenBAM must not run during the transition (v26.09 "not Alpenglow-ready", use 26.10+ after); Jito-Solana v4.3.0-jito.x / v4.3.2-jito builds published. No Jito statement on shreds/Rotor found. — [Jito docs](https://docs.jito.wtf/lowlatencytxnfeed/); [Solana Compass](https://solanacompass.com/news/jito-details-bams-alpenglow-plan-maintenance-mode-for-all-mainnet-nodes-no-firebam-during-the-transition)
- Triton: Yellowstone `v16.0.0-rc10+solana.4.3.0` with bank-aware buffering is the recommended build (its gRPC footer message "does not yet forward certificates"); Triton's shred product page and docs make no Alpenglow/Rotor statement. — [solana.com](https://solana.com/upgrades/alpenglow); [Triton docs](https://docs.triton.one/chains/solana/shred-streaming)
- Helius: Alpenglow explainer (above) and 4.3 coverage; shred/LaserStream docs make no Rotor migration statement beyond "Turbine will be replaced by Rotor". — [Helius](https://www.helius.dev/blog/alpenglow)
- DoubleZero: no Alpenglow/Rotor announcement located; its network carried ~62.6 % of mainnet stake (Aug 2026) and Edge is the Jito-designated successor feed. Anza/Helius describe Rotor as multicast-compatible, which is DoubleZero's delivery model. — [Solana Compass](https://solanacompass.com/news/doublezero-foundation-turns-two-626-solana-stake-sec-no-action-letter); [Helius](https://www.helius.dev/blog/alpenglow)

### Inferences
- For a shred-fed trading box, 21 Oct 2026 changes nothing about packet format, FEC sets, or who sends shreds; the decoder changes are (i) no tick entries (so do not use ticks to estimate slot position; a 64-tick slot clock derived from `SHRED_TICK_REFERENCE_MASK` will stop being meaningful), (ii) no vote transactions (less decode work, fewer bytes per batch, so the 50 ms coalesce timeout may bind more often in quiet slots), (iii) block header/footer markers in the shred stream, (iv) occasional second bank per slot (`bank_id`) once 4.4 ships, (v) `confirmed` collapsing into `finalized` ~150 ms after the slot.
- Fast leader handoff (4.4) lets the next leader start building before the parent is finalized; combined with 200 ms slots this shortens, not lengthens, the window to react within a given leader's turn.
- When Rotor ships: propagation to staked relays should get faster (single hop, ~2 ms to 80 % of stake in simulation) and more uniform, which erodes the edge of "shreds from a root-adjacent validator" that every relay vendor sells today; the unified shred type means every deshredder (Agave `Shredder::deshred`, jito deshred.rs, sol-shred-sdk) must be rewritten; whether non-staked subscribers get a defined place in Rotor is unspecified, so shred vendors will likely still be the only route for a non-validator box. This is inference; no vendor has published a Rotor plan.

### Gaps
- The Alpenglow whitepaper v1.1 PDF (Rotor section: Γ/γ parameters, PS-P sampling, handling of non-voting nodes) could not be fetched; Rotor's SIMD does not exist yet.
- No statement from Jito, Triton, Helius, Shreder, Everstake, BlockRazor or DoubleZero on how their shred products will change under Rotor.
- Whether Jito-Agave/BAM leaders will differ from Agave in slot-end behaviour after fast leader handoff is undocumented.
